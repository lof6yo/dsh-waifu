# ADR-048：演出编排（剧本引擎 / 演员 / 编排器三层）

- 状态：已采纳（Accepted）；P1（单标签帧 + `director.ts`）、P2（`timeline.ts` 谱子）、P3（播放器按段执行 cue）、P4（句中 cue）已实现，等 spike 数据定稿
- 日期：2026-11-07

## 背景

到 v1 为止，「模型说的台词」「模型挑的表情/动作」「真的演出来的东西」是三套各自为政的代码：

| 环节 | 位置 | 现状 |
|---|---|---|
| 解析标签 | `src/ai.ts` `parseLeadingTags` / `consumeLeadingTags` | 只认开头最多 3 个标签，正文里的标签直接丢 |
| 切句与转发 | `src/speak.ts` `runSpeakPipeline` | 每段只 `stripInlineTags`，句中标签既不播也不上报 |
| 应用演出 | `src/client/index.ts` `applyTags` / `startMotionWithPriority` | 收到就 FORCE 播，`stopAllMotions()` 打断上一个 |

后果已经在实际使用里出现过两次：

1. **一轮发两个 `tags` 帧**：模型分块吐标签（`[blush` + `][Sway]`）时每个块各发一帧，第二帧把第一个动作拦腰砍断（抽搐）；验收脚本只记最后一帧，导致「表情 0/4」的假数据。
2. **模型想「演一段」但表达不了**：标签只能写在开头，没法说「这句先别动，下一句再摇头」。

同时，提示词、历史、场景句的组装也散在 `systemPrompt` / `buildSceneMessage` / `historyMessages` / `assembleRequest` 四个函数里，改提示词只能靠读整段报文，没法钉住行为。

## 决策

**1. 三层职责，边界固定：谁决定「演什么」与「能不能演」分开。**

| 层 | 是什么 | 位置 | 性质 |
|---|---|---|---|
| 剧本引擎 `director` | 人设 + 记忆 + 目录 + 场景 + 历史 → 一次请求的剧本 | Host，纯函数 | 只决定「演员看到什么」 |
| LLM 演员 | 说什么台词、配哪些标签/位置 | 外部模型 | 只决定「演什么」 |
| 编排器 `timeline` + 播放器 | 台词分几十段、标签归哪段、来不来得及演 | Host（谱子）+ 浏览器（执行） | 只决定「能不能演、什么时候演」 |

**2. 编排器禁止做语义判断。** 它不许「从台词推测他很生气，于是选 `angry`」——那是导演的活，重演 ADR-046（宿主替角色推导状态）已被用户否决。编排器只做四件事：解析、排序、归属、丢弃/降级。降级是事实（「队列满」「音频只有 1.4 秒」），不是审美。

**3. 跨进程只有一个决策者。** Host 出**声明式谱子**（`clause { index, text, cues }`），浏览器只当执行器（放音频、按段执行 cue）。浏览器不重新解析文本、不自己决定顺序；否则两台状态机迟早不一致。

**4. 一轮只下发一个 `tags` 帧。** 开头的标签先攒着，正文出现时合并去重后一次交出（`cues` 里也因此只有一个「段 0 的开场演出」）。

**5. cue 归属规则：标签归属它之后的第一个台词段。** 于是：

- 开头连写的标签自然等于「第 0 段的 cue」，与旧行为完全等价；
- 将来允许句中标签时，`[ShakeHead]` 插在两句之间就等于「下一段才摇头」，不需要新语法。

**6. 段边界不由编排器发明，直接复用 TTS 的句读切分。** 段的序号就是音频序号——口型、气泡、动作共用同一个时钟，没有第二套时间轴。

**7. 播放器策略（P3）：表情 sticky、动作串行、可丢弃。**

- 表情：设了就保持到下一个表情 cue 或本轮结束（不再 4.2s 自动回落到事件态，否则「一直害羞」演不出来）；
- 动作：按段顺序串行，`motionFinish` 驱动；队列上限 2，超过就丢最旧；
- 绑定：cue 在「该段音频开始播」时执行（无 TTS 时绑定到该段文字开始显示）；
- 丢弃必须留痕（控制台 `cue.dropped | queue full`）。

**8. 剧本引擎是纯函数，行为用 golden 哈希钉住。** 改动提示词必须在 `src/director.test.ts` 留下 diff；搬代码不许改行为（P1 的三份哈希就是搬迁当天的现场记录）。

## 实现记录

**P1（2026-11-07）**：`src/director.ts` + `src/time.ts` 抽出，`ai.ts` 857 → 590 行；`streamReply` 把开头标签攒进 `collected`，正文出现时合并去重只发一帧。剧本内容用 golden 哈希钉住（system / messages / payload 三份）。

**P2（2026-11-07）**：`src/timeline.ts` 的 `ClauseTimeline` 增量切段并给每段挂 `cues`；`speak.ts` 的 `buffer` / `nextIndex` / 局部 `flush` 全部交给它。等价性用**搬迁前现场录的帧序列**做快照（四类输入），`withoutCues()` 后逐帧相等。

**P3（2026-11-07）**：客户端按段执行，规则入 `src/client/cue-queue.ts`（纯函数，可单测）：

| 情形 | 行为 |
|---|---|
| `clause` 帧带 `cues` | 记进 `speakCues[段号]`；该段音频开始播时执行 |
| 没有音频的段 | `enterClause()` 按段号补执行，不漏演 |
| 旧 Host（无 `cues`） | `tags` 帧照旧立刻播；两种来源都到位时**只播 cues**，避免同一次演出执行两遍 |
| 表情 | sticky：保持到下一个表情 cue 或本轮结束（`clearStickyExpression()`），不再 4.2 s 自动回落 |
| 动作 | 串行队列，`motionFinish` 驱动；上限 `MOTION_QUEUE_MAX = 2`，满了丢最旧并在控制台记 `cue.dropped` |
| 等不到 `motionFinish` | `MOTION_WAIT_MS = 6000` 兜底，队列不会卡死 |
| 打断（隐藏页/气泡超时/卸载） | `stopSpeaking()` 清 cue 表、清队列、唤醒所有等待者、撤 sticky 表情 |

**P4（2026-11-07）**：提示词允许把标签写在需要它的那一句前面（不再只认开头），Host 侧三处改动配合：

| 改动 | 位置 | 理由 |
|---|---|---|
| 正文原样转发（句中标签不再提前剥掉） | `src/ai.ts` `streamReply` | 剥掉就没人知道这个动作属于哪一句了 |
| 标签归属再到 cue | `src/timeline.ts` `extractTags()` | 段内标签归本段；**段尾标签顺延给下一段**（`唔…别、[Nod]` 的摇头跟后半句） |
| 未闭合标签先扣住 | `src/timeline.ts` `push()` + `openTagStart()` | 否则 `[No` + `d]` 会先被念成半句话 |
| 标签词归一化 | `src/ai.ts` `resolveTag()` | `[脸红]` → `blush`；原来中文名原样透传，下游只认英文 id，等于没有表情 |

顺带修掉 v1 提示词里的自相矛盾：示例原来写 `[shy]`（不在目录里），现在换成真实 id。

**P5（2026-11-07）：把「等」挤掉（首声与首字）**。基线实测（`scripts/spike-latency.mjs`，4 轮，腰/搂住）：首字节 23 ms、clause0 1354 ms、**首声 2441 ms**、下行 144 KiB（音频占 95%）。两处结构性等待直接去掉：

| 改动 | 位置 | 效果 |
|---|---|---|
| 说到标点上就立刻成段（不再留一段等下一块） | `src/timeline.ts` `push()` + `tts.ts` `endsAtClauseBreak()` | 首段音频不必等第二个字/下一块；帧顺序与旧实现逐字节一致（既有快照仍全绿） |
| 台词文字到达即上屏，cue 仍等该段音频开始 | `src/client/index.ts` `requestSpeak()` | 气泡比「首声」早约 1 秒出现，用户不再对着空屏等合成 |

复测（重启后 10 轮，腰/搂住，同一脚本）：

| 指标 | 基线（4 轮） | P5 后（10 轮均值） |
|---|---|---|
| 首字节 | 23 ms | 约 20–37 ms（不变，本来就是本地 SSE） |
| **`clause0` − `tags`**（等下一个字的时间） | **约 478 ms** | **多数轮为 0 ms**（有轮 49/238 ms） |
| `clause0` | 1354 ms | 1136–1341 ms |
| **首声** | 2441 ms | **2030–2128 ms**（−0.3~0.4 s，轮间波动 0.9–3.5 s） |
| 下行 | 144 KiB（音频 95%） | 146–182 KiB（音频 96%） |

结论：能被代码挤掉的等待（凑下一块、等音频再露字）已经挤掉，`clause0` 现在基本等于 `tags`；剩下的首声延迟由 **provider 生成到第一个标点** + **TTS 合成一整个 mp3** 两段决定，代码侧没有可再挪的部分。下行体积没变（音频占 96%），要降只能动音频格式/码率，属于独立评估项（`response_format` 目前硬编码 mp3）。

## spike 结论（2026-11-07，12 轮实测）

提示词允许句中 cue 之后（`scripts/spike-inline-cues.mjs`，脸/腰/胸/头发 四组各 3 轮）：

| 指标 | 结果 |
|---|---|
| 有台词 / 带 cue | 12/12 · 12/12 |
| **cue 落在第 0 段之后（真正的句中 cue）** | **1/12** |
| 平均 cue 数 / 平均段数 / 平均字数 | 2.08 · 3 · 24 |
| `tags` 帧数 | 恒为 1（12/12） |
| 泄漏（正文出现方括号） | 0 |
| 平均耗时 | 2375 ms |

唯一一次句中 cue：`脸·捏` 第 1 轮 —— `[blush][ShakeHead]` 在第 0 段，`[whites]` 落在第 1 段（白眼跟着后半句出现，效果正是想要的）。

**判断：能力保留，但不为它做引导。** 31B 模型即使被允许，也几乎总是把标签全写在开头；这属于模型偏好，不是实现缺陷——真写在中段时链路已经能正确演（解析、归属、按段执行都实测通过）。因此：

- 提示词保留「可以写在需要它的那一句前面」的许可，不删（删了反而限制了更好模型的发挥空间）；
- 不把「句中 cue 比例」写进验收指标，也不为它加 few-shot；
- 不采用「按标点自动把动作挪到更合适的段」这类做法：那是语义判断，违反「演什么归模型」的分工。

## 取舍

- **为什么不在 Host 维护「正在播哪个动作」**：只有浏览器知道 `motionFinish`、音频时钟和渲染帧；Host 若镜像这份状态，就必须靠上报回填，等于把同一个状态存两份。宁可让 Host 只产出「谱子」，让最了解硬件的进程做执行。
- **为什么不改成 JSON 输出**：会毁掉 ADR-033 的首字低延迟（模型要先产出完整结构）并显著增加 token；方括号流式已经能用。
- **为什么段内不再拆细**：段的粒度由句读决定（4–24 字），再细会让 TTS 请求数暴涨（实测每句已 3.37 次请求）；首声延迟问题要单独解决（见 AI 工程师报告的 A1）。
- **丢弃策略的代价**：动作串行 + 队列 2 意味着长台词里的第 3、4 个动作不会出现。这是有意的——宁可少演，也不要动作排队排到下一轮，看起来像抽搐。
- **P2 的 `cues` 目前是冗余字段**：老客户端不认它，行为不变；等到 P3 换成按段执行，它才成为真正的契约。这条冗余是刻意的，让 Host 先上线、客户端后换。

## 影响

- 新增 `src/director.ts`（剧本组装，纯函数）、`src/time.ts`（时区换算）、`src/timeline.ts`（段 + cue）；
- `src/ai.ts` 缩到「调用 + 解析 + 记忆行」，对外导出保持不变；
- `src/speak.ts` 的切分逻辑交给 `ClauseTimeline`，段边界与旧实现逐字节一致（`src/timeline.test.ts` 用搬迁前现场录的帧序列做快照）；
- 客户端 P3 需要新增：cue 队列、`motionFinish` 驱动的串行、表情 sticky、丢弃日志；
- 测试：214 → 237（剧本 golden 10 条、单标签帧 3 条、时间线等价 10 条）。
- P4 之前必须先跑 spike：`gemma-4-31b-it` 在 `temperature=1` 下能否稳定写「句中 cue」（15–20 轮，统计泄漏率 0、平均 cue 数 1–3、id 合规 100%），数据不够就不改提示词。
