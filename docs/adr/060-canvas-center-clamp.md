# ADR-060: 拖动范围按画布几何中心，计入页面 UI 缩放

## Status

Accepted

## Date

2026-11-09

## Context

ADR-059 把拖动/归位的夹取基准从「画布几何中心」改成「角色可见轮廓中心」，起因是真机上左/上方向拖不到一半出画。随后定位到真正的原因是**页面被外壳整体施加了 CSS `zoom`（实测 0.8）**：`right/bottom` 是缩放后的 CSS px，而夹取公式里用了未缩放的 `window.innerWidth`，导致「往左/上」的上限提前生效、往右/下却正常——这与当时观察到的「左/上不动、右/下能动」完全吻合（旧公式的 min 边界不含视口尺寸，所以没受影响）。

ADR-059 的可见轮廓偏移（真机测得约 −17,−34 px）又带来新的不对称：轮廓包围盒的左右边缘相对画布中心并不对称（头发/饰品偏一侧），用它当中心意味着「按包围盒各出一半」，但角色的身体本身偏在包围盒中心的一侧，于是左右极限对比时，往右会多出去十几像素——用户实机确认「到右边会出去更多一点」。

## Decision

1. 夹取/归位/捕捉恢复按**宠物画布（显示区）的几何中心**：逻辑画布 W×H 时 `right ∈ [−W/2, innerWidth/s − W/2]`、`bottom ∈ [−H/2, innerHeight/s − H/2]`，其中 `s = uiScale()` 为页面 UI 缩放（未缩放时 s=1，即 spec 原本的语义）。这样左右/上下对称，身体贴边时各出一半。
2. 所有与视口相关的换算都乘除 `s`：`homePositionFromConfig` 用 `viewport × pct / s − W/2`，捕捉为其逆运算 `(right + W/2) × s / viewport × 100`。
3. 拖动位移 `dx / s`、`dy / s`，保证视觉上 1:1 跟手。
4. `uiScale()` 运行时用 `canvas.getBoundingClientRect().width ÷ 逻辑画布宽` 测量，取不到或异常时回退 1。
5. ADR-059 的离屏 alpha 包围盒测量保留为**调试信息**（调试面板仍显示 `vis:`/`bbox:`），不再参与夹取；`c:` 行改为画布几何中心的屏幕坐标。

## Alternatives Considered

### 备选方案 A：保持可见轮廓中心（ADR-059 现状）

- Pros：按包围盒左右各出一半，轮廓在屏幕外的比例左右相等。
- Cons：轮廓包围盒相对画布中心不对称，角色身体偏在一侧，左右极限对比时一侧明显多出；用户实机反馈不对称。
- Rejected：几何中心更符合「显示区中心可以在整个 web 范围移动」的既有语义，且身体左右对称。

### 备选方案 B：继续不用 `s`，只把可见轮廓换成画布中心

- Pros：改动最小。
- Cons：真机页面缩放 0.8 时左/上仍会提前停住（本次问题的根因没修）。
- Rejected：必须把 UI 缩放计入。

## Consequences

- 正面：页面被外壳缩放时，四边都能拖到画布一半出画；左右/上下对称；普通桌面（s=1）行为与旧版一致。
- 代价：`homeRight/homeBottom` 与「捕捉」按视觉视口百分比换算，页面缩放存在时数值与 CSS px 不成简单比例；角色轮廓左右不对称（头发/饰品）时，左右极限看到的发丝多少仍会略有差异，但身体是对称的。
- 兼容：ADR-059 的 `vis:`/`bbox:` 仍显示；`visualOffset` 不再影响位置。
